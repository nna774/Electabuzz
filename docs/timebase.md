# 時間基準 — この設計の最重要点

## なぜ既存方式では成立しないか

既存は `sample_rate_mhz` を**公称値**として持ち、サンプル時刻を
`batch_start_us + i × 1e6/rate` で導出する
([wire.py:37-40](https://github.com/nna774/NamazuHaUrokoGaNai/blob/master/lambda/common/wire.py#L37-L40),
[design.md](https://github.com/nna774/NamazuHaUrokoGaNai/blob/master/docs/design.md) 93行目)。
加速度計としては完全に正しい。ESP32 の水晶が ±20ppm 狂って実サンプルレートが
100.002Hz でも、計測震度は何も変わらない。

**しかし周波数測定ではサンプルレート誤差がそのまま測定値の誤差になる。**
位相推定はサンプル列を時間軸として使うので、

```
サンプルレート誤差 ε  →  測定周波数の誤差 = ε × f_nominal
```

±20ppm は **50Hz に対し 1.0mHz**(60Hz なら 1.2mHz)。目標 ±1mHz をぎりぎり満たさない。
そして時刻偏差の積算では致命的になる。誤差の秒数は周波数に依らないので、東西で軽減しない:

```
20ppm × 86400秒 = 1.7秒/日 の「偽の」時刻偏差が積み上がる
```

日本の系統の実際の時刻偏差は数秒の範囲に制御されている。同じ桁の偽信号が乗る
ということは、**測定値が完全に無意味になる**という意味だ。

## 分けて理解すべき3つ

- **短期の分解能・安定度** — サンプルレート確度に依存しない。同一サンプル列内の位相差
  だけを見るので、水晶が狂っていても細かい変動は綺麗に見える
- **周波数の絶対確度** — サンプルレート確度に比例。0.1mHz なら 1.7ppm 以下が必要
- **時刻偏差の積算** — 「サンプルレートの真値を連続的に知り続ける」ことを要求。最も厳しい

## NTP だけで足りるか

原理的には足りる。NTP は**長期ドリフトを持たない**基準なので、サンプル数を NTP 時刻に
長時間回帰すれば実効レートが求まる(±5ms ノイズ、1時間窓で 1.4ppm、1日窓で 0.06ppm)。

だが採らない。理由は確度そのものではなく**検証可能性**だ。

- [config.h:73](https://github.com/nna774/NamazuHaUrokoGaNai/blob/master/firmware/src/config.h#L73) のコメントが
  正しく指摘している通り水晶ドリフトは ppm 級。それを NTP の slew で吸収する設計
  (`SNTP_SYNC_MODE_SMOOTH`)は、**システム時刻の進む速さ自体が制御対象**という意味であり、
  それをレート基準に使うのは筋が悪い。生の `esp_timer` カウンタと NTP オフセットを
  別々に記録して自分で回帰する必要がある
- WiFi 往復遅延の非対称性はバイアスとして残り、大きさを自分で示せない
- 自分の測定がどこまで正しいかを示せない測定器は、測定器ではない

`SNTP_SYNC_MODE_SMOOTH` 自体は周波数版でも必要(バッチ境界が飛ぶと困る)。既存判断は正しい。

## 採る方式: GNSS 1PPS を同じ ADC でサンプリングする

PCM1808 はステレオ ADC である。これを使う。

```
L ch ← 商用波形 (AFE経由)
R ch ← GNSS 1PPS (分圧してレンジに収める)
```

**同一サンプルクロックで両方を測る**ので、GPIO 割り込みジッタもタイマ較正も不要になる。
実効サンプルレートは「PPS エッジ間のサンプル数」から直接出る。エッジ位置はサンプル間
補間で決まるので分解能はサンプル周期以下。単発で数µs = 数ppm、長時間回帰で ppb 級。

PCM1808 は DC 除去の HPF を持つので矩形波は微分されるが、**むしろ鋭いピークになって
エッジ位置が取りやすくなる**。振幅の絶対値は不要。

この方式の良さは、**firmware に新しい時刻キャプチャ機構を一切持ち込まないこと**だ。
「サンプル列だけが時間軸」という既存の単純な構造を保ったまま、その目盛を GNSS に繋げる。

代替(方式B): **MCPWM の capture submodule** で PPS をハードキャプチャ。
ジッタは数十ns だが、サンプルクロックとキャプチャクロックという2つの時間軸を持つ
ことになる。方式Aが駄目なときの逃げ道。

> **GPTimer+ETM は使えない。ESP32-S3 に ETM(Event Task Matrix)は無い。**
> ESP-IDF の ETM ドキュメントは esp32c6 では存在するが **esp32s3 では 404** であり、
> `components/soc/esp32s3/include/soc/soc_caps.h` に `SOC_ETM_SUPPORTED` の定義も無い。
> **方式B の手段は MCPWM capture のみである。**
>
> ただしこれは退避先の喪失を意味しない。**MCPWM capture は無印 ESP32 にもあり
> （`SOC_MCPWM_SUPPORTED 1`）、W53SA 氏の先行例が実際に動かしているのはこれだ。**
> 「動いている先行例がある」という方式B の価値は無傷で残る。
>
> なお ESP32-S3 では `mcpwm_capture_timer_config_t::resolution_hz` が無効で、
> **capture timer の分解能は APB クロック固定**になる（80MHz = 12.5ns 刻み）。
> PPS のキャプチャには十分だが、設定できると思って書くと動かない。

## 時間基準を差し替え可能にする (GNSS 到着前に動かすための設計)

**結論から言う。PPS が無くても全体を動かせる。しかも捨て仕事にならない。**
条件は一つだけだ。**`fs` を定数として書くな。最初から「測って報告する量」として作れ。**

### 時間基準を3実装のプラグインにする

```
TimebaseEstimator (interface)
  fsMicroHz()     現在の実効サンプルレート推定 [µHz]
  residualNs()    推定の 1σ [ns/s] — 確度の自己申告
  obsCount()      推定に使った観測数
  source()        NOMINAL / NTP / PPS
```

| 実装 | いつ使う | 確度 | 偽TE |
|---|---|---|---|
| `NominalTimebase` | フェーズ1の疎通確認だけ | ±20〜100ppm | **1.7〜8.6 秒/日** |
| **`NtpTimebase`** | **GNSS 到着まで。かつ到着後も残す** | 0.1〜1ppm(1日窓) | **10〜90 ミリ秒/日** |
| `PpsTimebase` | GNSS 到着後 | ppb級 | µs/日 |

**中段が本命だ。** 系統時刻偏差の実変動は秒オーダーなので、**偽TE が数十ms なら信号より
1〜2桁小さい。つまり NTP 時間基準の TE は「意味のあるデータ」になる。**
設計書は既に「NTP は原理的には足りる(1日窓で 0.06ppm)」と認めており、退けた理由は
確度ではなく**検証可能性**だった。**暫定運転の時間基準としては、その留保は問題にならない。**

### NtpTimebase は捨て仕事ではない。到着後も3つの役割が残る

1. **PPS 喪失時の holdover。** リスク5(屋内で fix を維持できるか)に対して、本設計書は
   これまで「フラグを立てて捨てる」しか答えを持っていなかった。**NTP 時間基準があれば
   fix が落ちた区間を 1ppm 級で埋められる。空白ではなく劣化として扱える**
2. **`fs` の独立クロスチェック。** PPS と NTP は物理的に無関係な経路で同じ `fs` を推定する。
   一致すれば方式Aが効いている証拠、食い違えばどちらかが壊れている。
   **二重測定を諦めた本設計に、時間基準についてだけ二重系が手に入る**
3. **自分がどの水晶に乗っているかの実測。** 後述の通り、それは今のところ分かっていない

### 実装上の一点: システム時刻に回帰してはいけない

`SNTP_SYNC_MODE_SMOOTH` は**システム時刻の進む速さ自体を制御対象にしている。**
それに回帰したら、測っているのは水晶ではなく slew ループだ。

**測定専用の SNTP クライアントを別に持て。** システム時刻を一切触らず、
`(累積サンプル数, NTP時刻, RTT)` の三つ組を記録して自分で回帰する。
RTT の大きい標本を捨てられるのが自前実装の利点になる。

- **往復遅延の非対称バイアスは、定数なら回帰の傾きに乗らない**(切片に乗るだけ)。
  効くのはバイアスの**時間変動**だけで、これは経路変動オーダー。
  **ここが「NTP でも 1ppm を切れる」根拠だ**
- バッチのタイムスタンプ用のシステム時刻は従来どおり SMOOTH のままでよい。**役割を分ける**

### 実装の契約 (`firmware/lib/Timebase/`)

`TimebaseEstimator`（インタフェース）/ `NtpTimebase`（回帰）/ `MeasuringSntp`（測定専用の
SNTP クライアント）。**回帰は Arduino に依存しない**ので `test/run.sh` がホストの g++ で走る。
実機で確かめる必要が残るのは経路（WiFi と SNTP）だけになる。

**`residual_ns` の意味は「回帰の傾きの 1σ を ns/s に直したもの」に確定した。**
つまり実質 ppb であり、**経路のノイズそのものではない。**
上表がダッシュボードに `±(tb_residual_ns × 経過時間)` を描かせている以上、整合する定義は
これしかない（経路ノイズは n と時間幅で割り算されて初めて確度になる）。
経路ノイズの方は診断用に `fitRmsNs()` として別に出す。**ワイヤ形式には載せない。**

**ただし `residual_ns` は誤差予算の全体ではなく下限である。** これは「この窓全体の平均傾きが
白色ノイズ仮定の下でどれだけ決まっているか」であって「今この瞬間の発振周波数が
どれだけ確からしいか」ではない。前者は √時間 で無限に下がるが、後者には物理的な床がある。
**29時間の soak で実測した床は 0.2 ppm 級**で、同時点の `residual_ns` の申告（0.005 ppm）
とは40倍離れていた（→ [log/2026-08-05-soak-first-day.md](log/2026-08-05-soak-first-day.md)）。
原因が水晶のふらつきか NTP 経路の非対称遅延かは区別できていないが、**運用上の結論は同じで、
`NtpTimebase` を信じてよいのは 0.2 ppm 級までだ。** 定義は変えない
（不確かさ帯と整合する定義は他に無い）。読むときにこの床を忘れるな。

**die 温度による補正は実装しない。** 同 soak で温度が 42〜57℃ を往復した区間から
温度係数を引くと `-0.044 ± 0.030 ppm/℃`(1.5σ、95%上限 0.105 ppm/℃)で**有意でない**。
最悪値でも die の振れ 10℃ ぶんで 1 ppm と上の床と同じ桁にしかならず、
**補正して得られるものが無い**（基板の自己発熱が支配するので die の振れは室温より小さく、
筐体に入れればさらに縮む）。

**不変条件をインタフェースの実装で守る。** 観測が 8点かつ 600秒に満たないうちは
`source()` が `kNominal` を返し、`fsMicroHz()` は**公称値をそのまま返す**。
中途半端な回帰の結果を「測った値」として出すと、`source` が `NOMINAL` でも下流が信じる。
**600秒は「使ってよいか」の下限であって「十分か」ではない。十分かは `residualNs()` が答える。**

標本を捨てる条件は4つ。**捨てた数は `rejectedCount()` で見えるようにしてある**
（黙って捨てると経路の劣化に気づけない）。

| 条件 | なぜ |
|---|---|
| 往復遅延 > 150ms | 明らかな詰まり。**自前実装にした最大の利点がこれで、lwIP の SNTP は RTT を見せない** |
| 往復遅延 > 実測最小の3倍 | 経路の素の速さを基準にする。最小値は観測ごとに 1/64 ずつ上へ緩める（まぐれの1点で以後を締め出さないため） |
| サーバ時刻が進んでいない | 重複・巻き戻り。回帰の x にできない |
| 回帰からの外れが 5σ（最低 20ms）超 | うるう秒の取り違えや1秒級の事故ひとつで推定を壊さない |

**ティックが逆行したら `reset()` する。** ティック源が切れたということなので、
**セッション境界で線を繋がない。**

回帰は Welford（逐次中心化）で積み、さらに `y` から公称ぶんを引く。傾きが「公称からの
ずれ」そのもの（100ppm でも 100 ticks/s 程度）になり、30日回しても残差平方和の桁が潰れない。

`MeasuringSntp` は送信タイムスタンプに乱数を置き、**応答の Originate Timestamp と
突き合わせてから採用する。** 古い応答や取り違えをここで落とす。

### wire format を今のうちに source 非依存にする

**まだ1バイトも記録していない今がやり時だ。** PPS 専用フィールドを一般化する
(実際の定義は [wire-format.md](wire-format.md) を参照)。

- `pps_count` → **`tb_obs_count`**、`pps_residual_ns` → **`tb_residual_ns`**。
  源に依らず「観測数」と「確度の自己申告」を意味する
- 予約領域に **`timebase_source` (u8)** を出す。**これが無いと、後から
  「このデータは規正済みか」が永久に判別できなくなる**

**すべて予約領域から出すので、GNSS が来た時点でヘッダは1バイトも変わらない。**
後段のパーサもダッシュボードも書き直さない。**これがこの節の要点だ。**

> **「測れなかった区間を測れたように見せない」という一線は、1バイトのフィールドで守られる。**

### TE は「保存する、提示は封じる」

累積位相は**どの時間基準でも有効な物理量**だ(サイクルを数えただけ)。保存は無条件に行う。
封じるのは派生量である TE の**提示**の方だ。

| `timebase_source` | ダッシュボードの振る舞い |
|---|---|
| `NOMINAL` | **TE を描くな。** 周波数変動の形と RoCoF だけ出す |
| `NTP` | 描いてよい。ただし **±(`tb_residual_ns` × 経過時間) の不確かさ帯を必ず併記する**(1日で ±10〜90ms) |
| `PPS` | 帯が µs 級に潰れる |

**グラフの上で帯が縮む瞬間が、GNSS を繋いだ日になる。それが一番正直な見せ方だ。**

### 事後補正の余地を無料で残す

`fs` の仮定値と **SoC 温度**を記録しておけば、GNSS 到着後に水晶の `fs(T)` 特性を実測して
**PPS 前のデータを遡って補正できる。** 完全には戻らない(NTP 回帰の残差は残る)が、
**記録が無ければ補正の可能性そのものが存在しない。1バイトの温度フィールドで買える保険だ。**

### 見落としていた前提: そもそも `fs` を決めているのは誰か

**PCM1808 は動作モードに関わらず SCKI(システムクロック、256/384/512 fs)を要求する。**
そして誰がそれを供給するかで、`fs` の出自が変わる。

- **モジュールに 12.288MHz の缶発振器が載っている個体は、それが master になる。**
  fs は 48kHz ちょうどだが、確度は**その缶発振器の公差(安価品で ±50〜100ppm、温度特性も悪い)**
- **ESP32 から MCLK を出す構成なら、fs は分数分周器で決まる。** 48kHz は 160MHz 系から
  割り切れないので、**公称 48000 と実際の設定値が数十ppm 食い違う。水晶とは無関係な誤差だ**

> **「APLL を使えば公称値にずっと近づく」という逃げ道は S3 には無い。**
> **ESP32-S3 の I2S は APLL を持たない。** `components/soc/esp32s3/include/soc/soc_caps.h` に
> `SOC_I2S_SUPPORTS_APLL` の定義が無い（**無印 ESP32 には `(1)` で存在する**）。
> つまり **APLL があるのは無印 ESP32 の方**で、S3 では選べない。
>
> **だが結論は変わらないし、困りもしない。** 公称値からの定数ずれは `NtpTimebase` の回帰が
> そのまま吸収する（回帰は傾きを測るので、`fs` が 48000 でなく 47998 でも正しく求まる）。
> 効くのは**安定度**だけであり、分数分周(PLL_160M)と APLL のどちらが安定かは
> **自明ではない**（APLL は fractional-N なので位相雑音が悪い可能性がある）。
> **フェーズ1.5 で測って決める話であって、チップ選定の理由にはならない。**
>
> むしろこの事実は本節の主張を補強する。**S3 では「fs はちょうど 48000」というふりが
> 物理的にできない。** それは正しい心構えを強制されているという意味だ。

**つまり「48000 と書いてある値」は二重に信用できない。** どちらの構成でも結論は同じで、
**`fs` は測れ。定数として持つな。** 前掲のプラグイン設計はこの事実そのものから要求されている。

> **方式Aは、どちらの水晶が master でも成立する。** 相殺は「信号と時間基準が同一クロックで
> 測られている」ことだけに依存し、**そのクロックの出自を問わない。**
> だから master/slave の選択は方式Aの成否に効かない。**効くのは PPS が無い期間の確度だけだ。**

**【フェーズ1で両構成を実測して決めろ】。** NtpTimebase があれば `fs` の実測値と安定度が
数字で出るので、どちらの水晶がましかは**測れば分かる**(設計書が一貫して採ってきた
「測ってから上げろ」と同じ手だ)。そして**一度決めたら PPS 到着後に変えるな。**
配線とクロック経路が変わり、それまでの検証がやり直しになる。

> **2026-08-07、実配線で決着した。** `gFs`(fs実測ppm)と`gXtal`(水晶ppm)は一致しないが、
> 差分が8点にわたり31.7〜32.9ppmとほぼ一定だった(`gXtal`自体は毎回動いていたにも
> 関わらず)。これは本節で予告した「水晶とは無関係な数十ppmのずれ」と定量的に一致し、
> **ESP32のMCLK(分数分周器)がSCKIを駆動している**と判定できた——モジュール搭載の
> 缶発振器が master なら、この差分が一定になる理由がない。→
> [log/2026-08-07-fs-wiring-verification.md](log/2026-08-07-fs-wiring-verification.md)

### R ch は最初から生かしておけ

**これが唯一の「後戻りできない」項目だ。ここだけは手を抜くな。**

- **I2S はステレオで初期化し、R ch も最初からサンプルして捨てる。** モノラルで作ると
  DMA のバッファレイアウト・サンプルの添字・後段の処理が全部変わる。
  **PPS を繋ぐ日に、一番バグを埋めやすい変更になる**
- R ch の分圧・帯域制限・**PPS 用ピンヘッダを基板に最初から載せろ**(部品5点)
- **未接続の R ch を浮かせるな。** バイアス網で Vcc/2 に落としておく。
  浮かせるとハムを拾い、「PPS らしき波形」が見えて無駄に悩む
- 捨てるのではなく **R ch のノイズフロアを記録しておけ。** PPS を繋いだ日の S/N の比較対象になる

## サンプリング機構は I2S DMA に置き換える

既存は [main.cpp:243-247](https://github.com/nna774/NamazuHaUrokoGaNai/blob/master/firmware/src/main.cpp#L243-L247)
で `esp_timer` を 1kHz、`ESP_TIMER_TASK` dispatch で回し、
[main.cpp:52-54](https://github.com/nna774/NamazuHaUrokoGaNai/blob/master/firmware/src/main.cpp#L52-L54) の ISR から
タスク通知している。ソフトタイマ dispatch なのでジッタがある。

周波数版では **I2S DMA** にする。サンプルクロックがハードウェア由来になりジッタが
消え、CPU は DMA バッファを掃くだけになる。
[design.md](https://github.com/nna774/NamazuHaUrokoGaNai/blob/master/docs/design.md) のオーバーサンプリング
(`kOversample=10` のボックスカー平均)による簡易アンチエイリアスも不要で、
**アナログ LPF + 高いサンプルレート**という素直な形になる。

## うるう秒: TE を UTC で測ると 1秒の偽ジャンプが出る

**見落としやすいが、系統時刻偏差にとっては致命的だ。**

TE は `cycles/f_nom - (t - t0)` で計算する。この `t` を UTC で取ると、うるう秒挿入時に
**UTC が1秒ずれる一方でグリッドはサイクルを数え続ける**ので、TE に 1秒の階段が現れる。
系統時刻偏差の実際の変動幅は数秒なので、**1秒の偽信号は誤差ではなく破壊だ。**

- 内部計算は **連続時系(TAI または GPS時刻)で行う**。UTC は表示のときだけ使う
- u-blox は現在のうるう秒数と挿入予告を報告するので、**イベントとして記録する**
- 2016年以降挿入はなく2035年までに廃止の見込みだが、**起きたときに黙って壊れる**種類の
  バグなので先に潰しておく
- これは後述の NTP サーバ側でも効く論点(leap smearing か step かの選択)

なお [main.cpp:97](https://github.com/nna774/NamazuHaUrokoGaNai/blob/master/firmware/src/main.cpp#L97) は
`if (!timesync::isSynced()) continue;` でサンプルを捨てているが、周波数版では
**捨てずにフラグを立てて出す**方がよい。holdover 期間そのものが後から見たい情報だからだ。
