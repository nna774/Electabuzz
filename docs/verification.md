# 検証

二重測定はしない。したがって**絶対確度をどう担保するかを明示的に埋める必要がある。**

## GNSS 到着前に到達できる検証 (先に切り分けておく)

**確度に関わらない検証項目は、GNSS が無くても全部通せる。** 待つ必要があるのは
絶対確度の一点だけだ。**待たなくてよいものを待つな。**

| GNSS 不要 | GNSS 必須 |
|---|---|
| **外部照合(系統挙動)** — W53SA 氏・powerk95 との**「形」とイベントの一致**。**相手も無基準なので、こちらの絶対確度は元より要件になっていない** | **絶対確度** — TP2 = 50.000000Hz の自己校正 |
| **Allan 偏差の短期側** — 安定度はサンプルレート確度に依存しない | Allan 偏差の長期側(NTP 回帰の帯で律速される) |
| 高調波耐性 / 実装間の一致 / 既存経路の非破壊 / 欠測ゼロ / 電源断耐性 | — |
| **`fs` の実測と安定度**(`NtpTimebase`) | `fs` の ppb 級同定 |

**外部照合が GNSS 不要側に丸ごと入るのが大きい。** 設計書はこれを「絶対確度の照合には
使えない。負うのは系統の実挙動を捉えているかであって確度ではない」と既に切り分けていた。
**その切り分けの配当が、ここで前倒しの形で返ってくる。**

## 最重要: GNSS の TIMEPULSE2 で自己校正する

**関数発生器では 0.1mHz を検証できない。** 一般的なベンチ発生器の時間基準は
TCXO で ±1ppm(50Hz に対し 50µHz)、水晶なら ±20〜50ppm。**目標確度と同じかそれ以下の
確度しかない器具で検証しても意味がない。** DDS モジュール(AD9833等)は更に悪い。

代わりに **GNSS の TIMEPULSE を基準信号源として使う。** u-blox の TIMEPULSE は
`CFG-TP5` で任意周波数に設定できる。

```
校正時:  受信機A の TIMEPULSE = 1 Hz         → R ch   … サンプルレート同定(通常運転と同じ)
         受信機B の TIMEPULSE = 50.000000 Hz → L ch   … GNSSトレーサブルな基準
```

**本番と完全に同じ信号経路で「GNSS にトレーサブルな 50.000000Hz」を測る。**
読み値が 50.000000Hz からどれだけずれるかが、そのまま系全体の絶対確度になる。
**AFE・ADC・DFT・位相 unwrap・累積位相の全段が検証範囲に入る。**

**受信機を2台使う理由。** R ch のサンプルレート同定と L ch の基準は**同時に必要**だ。
1台で TIMEPULSE を 50Hz にしてしまうと、その 50Hz を何に対して測るのかが循環する。
**この2台目に M8T の TIMEPULSE2 を充てるのは高すぎる**($100)。校正時に要るのは
「GNSS に同期した2つ目の TIMEPULSE」だけで、time-only モードは要らない。

- **段階1で買う安価なモジュールをもう1個(1,000〜2,500円)買えばよい。** これで足りる
- 別件の NTP サーバ用に受信機を2台買うなら、**校正時はそちらを一時的に借りればゼロ円**
- 2台は同じ GNSS に同期しているので、両者の関係は既知(これが成立の根拠)
- 校正時のみの接続なので、アンテナはスプリッタで分けるか、片方に付属パッチを付けて
  窓際に置くだけでもよい(校正は数分〜数十分の作業)

**基板設計への要求**: L ch の入力を「AFE 出力」と「外部基準入力(分圧・帯域制限済み)」で
切り替えられるジャンパかスライドスイッチを載せておく。**後付けが面倒な配線なので最初から
入れておけ。** 校正は一度で終わる作業ではなく、**疑わしい値が出たときに毎回立ち返る場所**になる。

## 先行実装: 友人 (W53SA 氏) のシステム — 構成が判明した

**[記事](https://www2.hatenadiary.jp/entry/2022/04/12/freqWatch)(2022-04)で公開されている。**
データ `www2.zxvf.jp/freqWatch/`、コードは GitHub。**東西の両方を測っている。**

| | **W53SA 氏** | 本設計 |
|---|---|---|
| **AC入力** | **サルベージした ACアダプタ** + LM393 ヒステリシスコンパレータ | **トランス式ACアダプタ** + AFE |
| 関西60Hz | ESP32、**MCPWM input capture**、80MHz カウンタ | — |
| 東京50Hz | AVR/ATTiny + Raspberry Pi | ESP32-S3 + PCM1808 |
| **測定方式** | **ゼロクロス検出** | **単一ビンDFT(Goertzel)** |
| **時間基準** | **無し**(NTP も GPS も PPS も使わない) | **GNSS 1PPS を同一ADCでサンプリング** |
| 分解能 | 約 0.0001 Hz | 0.1 mHz 級 |
| **絶対確度** | **±10 ppm(水晶公差で律速)** | GNSS 規正、ppb 級を狙う |
| 出力 | 瞬時周波数のみ。**時刻偏差は出していない** | **累積位相が第一級データ** |
| 可視化 | 1分値グラフ(Chart.js)、10分中央値(VictoriaMetrics + Grafana)、Go | S3 + Lambda + rollup + CloudFront |

**独立に同じ結論へ到達している点が二つあり、本設計の判断の傍証になる。**

1. **ACアダプタを絶縁センサとして使う。** 経験のある人間が同じ選択をしている
2. **ESP32 の MCPWM input capture。** これは本設計の**方式B そのものだ。方式A(PPS を
   R ch で同時サンプリング)が駄目だったときの退避先に、動いている先行例がある**

**決定的な差は時間基準だ。** 「時刻偏差を出していない」のは選択ではなく**出せない**から。
時間基準が無ければ ±10ppm がそのまま積算され、**0.86 秒/日**の偽の偏差が出る。
系統時刻偏差の実変動が数秒である以上、意味を成さない。
**本設計が GNSS 規正に投資する理由が、実例として目の前にある。**

## 外部照合: 友人の東京50Hz 系との比較

**相手に時間基準が無い**(ゼロクロス・±10ppm)ので、**ΔTE の傾きが 0 に収まるかを見る、
という照合はできない。ΔTE は必ずランプになる。** 傾きは相手の水晶オフセットの実測値だ。

### 何が比較でき、何ができないか

| 比較対象 | 可否 | 理由 |
|---|---|---|
| **周波数変動の「形」** | **◎ これをやれ** | 乗算バイアス 10ppm は変動の形を変えない。20mHz の偏移は 20.0002mHz に見えるだけで区別がつかない |
| **系統イベントの一致** | **◎** | 逸脱・RoCoF・発生時刻が一致するか。**両者が本物の系統挙動を見ている証拠になる** |
| 絶対周波数の一致 | ✗ | 相手は ±10 ppm(50Hz で 0.5 mHz)。**こちらの方が正確なので、照合ではなく相手の較正になる** |
| ΔTE が平坦か | ✗ | **必ず傾く。傾き = 相手の水晶オフセット** |

### ΔTE のランプは捨てるのではなく読む

`f_相手 = f_真 × (1 + ε)`、ε は水晶オフセット(±10ppm、温度でゆっくり変動)。よって

```
ΔTE(t) = TE_自分(t) − TE_相手(t) ≈ −ε · t      ← 傾き ε の直線
```

- こちらが TP2 自己校正で確度を独立に担保できていれば、**この傾きは相手の水晶オフセットの
  実測値**になる。相手にとって有用な情報であり、同時に**こちらの連鎖が生きている証拠**でもある
- **見るべきは傾きそのものではなく、傾きの安定性と残差だ。** 直線を引いて残差を取ると、
  そこに両者のノイズと本物の不一致が出る。**綺麗な直線で、傾きが温度と相関して緩やかに
  動くなら両系とも正常**
- **ランプが不規則に折れたり跳んだりしたら、どちらかに異常がある。** これが実質的な検出器になる

### 訊くこと (記事で判明した分は削除済み)

1. **東京50Hz 系はまだ稼働しているか。** 記事は 2022年。**照合に使えるのは東日本側だけ**
   (東西は別の同期系統。連系は周波数変換所(FC)経由の直流のみで、交流的に繋がっていない。
   西日本と比べても測定器の検証にはならない)
2. **生データを絶対時刻付きで交換できるか。** 相手は瞬時周波数しか持たないので、
   **こちらで積分して TE 相当を作る**ことになる。サンプル間隔・欠測の扱い・タイムスタンプの
   付け方(何の時刻か)を確認する
3. **ゼロクロス方式で高調波起因のジッタが実際どう出ているか。** 設計書がゼロクロスを
   退けた根拠(頂部の潰れた波形で数十µs のジッタ)について、**実測値を持っている可能性がある。**
   ヒステリシスコンパレータでどこまで抑えられたかも
4. **MCPWM input capture の実装上の落とし穴。** 方式B の退避先として先に聞いておく
5. 実装で何が壊れたか、地元の商用波形がどう見えるか

> **東西の差そのものは本物の物理量だ。** `TE_東 − TE_西` は二つの系統の時計がどれだけ
> 離れていくかの実測値で、**ダッシュボードのコンテンツとしては面白い**
> (検証ではなく観測対象として扱う)。相手が両方持っているのは好都合。

### 注意: 相関した誤差は相殺しない

一致が常に良い知らせとは限らない。両者が同じ誤差要因を共有していれば仲良く同じ方向に
間違う。**幸いこの組み合わせは方式が全く違う。** 時間基準・検出方式・MCU・信号処理の
すべてが独立なので、**形が一致すれば強い証拠になる。**

**絶対確度の担保は TP2 自己校正が負う。この照合が負うのは「系統の実挙動を捉えているか」
であって、確度ではない。役割を混ぜるな。**

## 検証項目

| 項目 | 方法 |
|---|---|
| **絶対確度(最重要)** | **上記 TP2 = 50.000000Hz を L ch に入れ、読み値の偏差を測る。GNSSトレーサブル** |
| サンプルレート同定 | `pps_residual_ns` を監視。数十ns に収まるか |
| 安定度・系統誤差の検出 | Allan 偏差。平均時間に対して期待通り改善するか。**折れ曲がりが出たら系統誤差の証拠** |
| **外部照合(系統挙動)** | **友人(W53SA氏)の東京50Hz 系と比較**(前節)。**周波数変動の「形」とイベントの一致を見る。絶対値の照合には使えない**(相手は無基準・±10ppm)。ΔTE のランプの傾きは**相手の水晶オフセットの実測値**として読む |
| 外部照合(補助) | **[powerk95](https://powerk95.net/50Hz/) の公開値**(東日本50Hz、周波数・RoCoF・時差、CSV あり)。東電PG/OCCTO は周波数を公開していない。方式が不明なので補助的に使う。**2026-08-09に初実施、相関0.993(共通1788点、30分間)を確認**(→ [log/2026-08-09-powerk95-external-verification.md](log/2026-08-09-powerk95-external-verification.md))。副産物としてバッチ境界の残存ジャンプ([risks.md](risks.md)リスク12)を発見した |
| 高調波耐性 | 基本波 + 3次/5次高調波を合成入力し読み値が動かないことを確認(`tools/gen_synthetic.py` 流用) |
| 実装間の一致 | `tools/backtest_gridfreq.py` で C++ と Python を照合 |
| 既存経路の非破壊 | ~~切り出し直後の `pytest` 緑 + 実機焼き直しでの着弾確認~~ **2026-08-03 に確認済み**(v1.0.0 タグを打つ条件だった) |
| バージョン pin の実効性 | **共有レポに次の版(v1.1.0)を入れたとき**、地震計を再ビルドしても **v1.0.0 が引かれる**ことを確認(ブランチ追従になっていないことの証明)。**その版を切るまでは未検証のまま残る** |
| 欠測ゼロ | WiFi を数時間切断 → 復帰後 `series/` に穴がないこと |
| 電源断耐性 | 稼働中に電源を抜き、`session_id` の不連続が正しく記録されること |
