# soak の一昼夜が閉じた — 水晶は +3.9ppm、温度依存は無し、そして `residual_ns` には床がある

フェーズ1.5 の soak（`firmware/src/main.cpp` + `tools/soak_capture.py`）を 2026-08-04 13:43 に
開始し、29.4時間ぶん（668点、棄却5点）まで回した時点の読み。**soak はまだ止めていない。**

**この soak が測っているのは ESP32-S3 の 40MHz 水晶であって `fs` ではない。**
ADC も AC 入力も繋がっていないので、リスク10 は片方しか埋まらない。

## 1. 水晶の実 ppm

ファーム申告と、CSV から独立に引き直した回帰が一致した。

| 経過 | n | `ppm` | `resid_ns` | 換算 |
|---|---|---|---|---|
| 18分 | 8 | 11.24 | 5914 | 5.9 ppm |
| 53分 | 22 | 3.14 | 881 | 0.88 ppm |
| 2h54m | 66 | 3.31 | 114 | 0.11 ppm |
| 7h53m | 181 | 3.65 | 25 | 0.025 ppm |
| **29h25m** | **668** | **+3.88** | **5** | **0.005 ppm** |

独立回帰は **+3.8873 ± 0.0055 ppm**。σ ∝ T^-1.5 の通りに落ちている。

**手元の個体は +3.9 ppm。** ±10ppm 仕様の部品として素直で、外れ個体ではない。

**初期の +11.2 ppm を信じなかったのが正しかった。** あの時点の `resid_ns` は
5914（= 5.9 ppm）で SN 比が 2 しかなく、最終値とは 1.4σ でしか矛盾していなかった。
**`fs` の隣に `residual_ns` を置いた設計の値打ちがそのまま出た事例**として記録しておく。

## 2. 温度依存は検出できなかった

`temp_c` は自己発熱で 57℃ まで上がったあと、深夜に **42℃ まで落ちて朝に 54℃ へ戻った。**
往復したので**温度と時間の共線が解け、初めて温度係数を引ける**ようになった
（単調降下しかしていない間は、原因が何であれ遅いドリフトが全部「温度のせい」に見える）。

1.75時間窓の局所 ppm を die 温度に加重回帰した結果:

```
温度係数 -0.044 ± 0.030 ppm/℃   (1.5σ)
→ 95%上限 |α| < 0.105 ppm/℃     (46.2〜56.2℃ の範囲で)
```

**有意ではない。** 窓幅を 1時間に変えると符号すら +0.024 に反転する。ノイズだ。

AT カット水晶の三次特性からは、変曲点 25℃・動作 55℃ なら -0.3 ppm/℃ 前後が
理屈上の期待値になる。**実測はそれより1桁小さい。** 変曲点が高い個体を引いたか、
モジュール上の水晶が想定と違うかだが、**どちらでも運用上の結論は同じなので追わない。**

**結論: 温度補正は実装しない。** 上限 0.1 ppm/℃ × die の振れ 10℃ = 1 ppm が最悪値で、
これは後述の床（0.2 ppm）と同じ桁に収まる。**補正して得られるものが無い。**

なお **die 温度の振れは室温の振れよりずっと小さい**（基板の自己発熱が支配している）。
筐体に入れればさらに圧縮される方向なので、この結論は設置後も緩まない。

## 3. `residual_ns` には床がある — これが今回いちばん重要

局所 ppm を並べて χ² を取ると、**各窓が自分の誤差棒より余分にばらついている。**

```
chi2/dof = 1.65 (16窓)   →  超過ばらつき σ_excess ≈ 0.18 ppm
```

つまり **1〜2時間スケールでは傾きが 0.2 ppm 級でふらついている。**
一方その時点の `resid_ns` は 5 ns/s = 0.005 ppm を申告している。**40倍の乖離だ。**

**これは矛盾ではなく、定義通りの挙動である。**
`residual_ns` は「**この窓全体の平均傾きが、白色ノイズ仮定の下でどれだけ決まっているか**」
であって「**今この瞬間の発振周波数がどれだけ確からしいか**」ではない。
前者は √時間 で無限に下がるが、**後者には物理的な床がある。**

超過の原因は2つあり、**この soak では区別できない。**

- 水晶が実際にふらついている
- **NTP 経路の非対称遅延がゆっくり動いている**
  （`fit_rms_ns` は 2.8ms → 4.4ms へ増えている。WiFi 越しなら十分ありうる）

**区別する必要も無い。** どちらでも運用上の結論は同じで、
**`NtpTimebase` の実用的な下限は 0.2 ppm 級**であり 0.005 ppm ではない。

### この数字が要件に対してどうか

| 量 | 0.2 ppm が意味するもの |
|---|---|
| 周波数 | 50Hz × 0.2ppm = **10 µHz**。分解能としては十分すぎる |
| 系統時刻偏差 | 0.2 ppm の**ふらつき**は積分すると打ち消し合う。効くのは長期バイアスの方で、そちらは ±0.006 ppm で刺さっている = **0.5 ms/日未満** |

**フォールバックの時間基準としては要求を大きく上回っている。**
そして**これは方式A（PPS を同一 ADC で拾う）を採る理由の裏取りでもある** —
あちらは水晶の誤差が一次で相殺するので、この床を踏まない。

## 4. 何が覆ったか

覆っていない。**`residual_ns` の定義（回帰の傾きの 1σ）は変えない。**
ダッシュボードの不確かさ帯と整合する定義はこれしかない、という判断は生きている。

変えたのは**その数字をどう読むかの注意書き**で、[timebase.md](../timebase.md) に
「`residual_ns` は誤差予算の全体ではなく下限である」と実測値つきで足した。

## 5. 何が次に可能になったか

- **`NtpTimebase` の実力が数字で確定した。** GNSS が死んでいる間に `NTP` へ落ちたとき、
  どこまで信じてよいかが言える（0.2 ppm 級）
- **温度補正を実装しない判断が固まった。** 実装しないことを実測で正当化できる
- **PCM1808 到着後の `fs` 測定で、比較対象になる数字が手元にある。**
  ESP32 が SCKI master の構成なら `fs` の ppm はこの +3.9 ppm を引き継ぐはずで、
  **そうならなければ配線かクロック経路が想定と違う**と即座に分かる

soak はこのまま回し続ける。**用も無く繋ぎ直すな**（macOS では open のたびに
基板がリセットされ、回帰が積み直しになる）。
