# バッチ起点のフレーム数を「処理時刻」でなく「窓完成の瞬間」で確定するよう直した

## 前回の修正だけでは足りなかった

[前回の修正](2026-08-08-batch-start-unified-timebase.md)(`unixUsAt()`でバッチ起点を
`gFs`の回帰に統一)を実機に投入し、20:21:57からのデータで検証したところ、**針は
減ったが消えていなかった。** 20分間で見ると:

- 20:21:56〜20:23:24: 4件連続で異常(2.66秒・-0.66秒・2.60秒・-0.61秒)
- 20:23:54〜20:24:54: 3件連続で正常(0.997〜0.999秒)
- 20:25:26〜20:25:54: また2件異常(2.37秒・-0.37秒)
- 20:26:24〜20:27:54: また4件連続で正常

異常が起きた瞬間はどちらも`tb_obs_count`(gFsが取り込んだNTP観測数)がちょうど
増えたタイミングと一致していた。**つまり一過性の起動直後ノイズではなく、
NTP問い合わせのたびに再発する構造的な問題**だと分かった。

## 原因: 「今」を読む場所が間違っていた

前回の修正は`timesync::nowUs()`を`gFs.unixUsAt(currentFramesEstimate())`に
差し替えたが、**どちらも「xQueueReceiveでバッチの最初のレコードを受け取った瞬間」に
評価する**という構造は変えていなかった。`gSntp.query()`(`firmware/src/main.cpp`の
NTP問い合わせ)は`kNtpTimeoutMs=2000`まで`loop()`をブロックしうる。この間、
Core1(`i2sTask`)は独立に動き続けてキューにレコードを積むが、**Core0がキューを
処理できるのはブロックが解けたあと**になる。バッチの最初のレコードがこのタイミングに
重なると、「窓が実際に完成した瞬間」と「Core0がそれを処理した瞬間」の間に
最大2秒のズレが生じ、それがそのままバッチ起点の誤差になる。

**前回の修正は「どの時計を読むか」は直したが、「いつ読むか」は直していなかった。**

## 直したこと

`WindowRecord`(Core1→Core0のキューで渡すレコード)に`framesAtEnd`を追加した。
これは**窓が完成した瞬間の累積フレーム数**で、`pumpI2s()`(Core1)が
`g->addSample(l)`が`true`を返した**その場**で確定させる
(`framesBeforeThisRead + i + 1`。`gFrames`の書き手はCore1だけなのでロック無しで
読める)。バッチ起点は`gFs.unixUsAt(rec.framesAtEnd)`から計算するよう変更し、
**Core0の処理遅延を経路から完全に排除した。**

不要になった`currentFramesEstimate()`(「今」を外挿する版)は削除した。

## 何を確認したか

`s3`/`gridfreqtest`/`record`の3 envともビルド成功。20:31:30に実機へ焼き直した。
**境界dtが今度こそ揃うかの実機確認はこれから**(NTP問い合わせを複数回またぐ
時間走らせて検証する必要がある——前回の教訓で、数分の観測では再発を見逃す)。
