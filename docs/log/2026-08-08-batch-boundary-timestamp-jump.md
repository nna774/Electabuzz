# ダッシュボードの「針」ノイズの原因を特定した(バッチ境界のタイムスタンプ、未修正)

## 何を見つけたか

C1(LPF)実装後もダッシュボードのグラフに単発の鋭いスパイクが残る、という指摘を受けて
`/recent`のデータを精査した。過去30分・240点中、周波数が50Hzから0.15Hz以上外れた点は
1件(19:42:13、45.39Hz)。この点を`series/`の生バッチまで遡ると、**直前レコードとの
実時間差が1.0秒のはずが1.1016秒だった**——`session_id`は変わらず`DISCONTINUITY`
フラグも立っていない、つまりGoertzelのウィンドウリセットではない。

同じ30分間で類似の異常dtを全数走査すると**4件すべてがバッチの先頭(境界)で発生**
していた(2.42秒・**-0.41秒(時刻逆行)**・1.10秒・0.89秒)。`lambda/api/handler.py`の
隣接点フィルタは「dtが公称値の0.5〜2.0倍以内なら計算する」という緩い許容なので、
この程度のズレは素通りして異常な瞬時周波数(cycles差分/誤ったdt)を出力する。

## なぜ時刻が飛ぶか

`firmware/src/main.cpp`で新しいバッチを始める箇所(`gCurrentBatch->begin(timesync::nowUs())`)
が原因。**この装置には時刻源が2つあり、性質が全く違う。**

- **`gFs`(`NtpTimebase`)**: レコード間隔(1バッチ内の各レコードの仮想タイムスタンプ)を
  決めている。長時間のNTP往復回帰で`fs`をppm級まで詰めた、**滑らかで精度の高い**時刻源
- **`timesync`(`batch-uplink`の`TimeSync`)**: `batch_start_us`(バッチの先頭だけ)を
  決めている。lwIPのSNTPクライアント(`SNTP_SYNC_MODE_SMOOTH`)が`adjtime`で
  slew補正する**粗い壁時計**。ステップ補正は10秒超のズレでしか発火しない
  (`kTimeSyncStepThresholdSeconds`)ので、今回程度の1秒未満のズレはslewの範囲内

**バッチが1本完成するたびに`timesync::nowUs()`を都度読み直している。** 前バッチの
終端時刻に「経過した精密な時間」を足して次バッチの起点にする設計ではなく、**毎回
独立に粗い壁時計を読む**ため、その瞬間のSNTP補正状況(ポーリング間隔・RTTジッタ・
slewの途中経過)がそのまま`batch_start_us`のブレになって現れる。バッチ内(30レコード=
約29〜30秒)は精密な`gFs`ベースで滑らかだが、**バッチ境界だけ粗い時計に切り替わる**
という構造的な不整合がスパイクの正体。

## C1との関係

**無関係と確定した。** C1はAFEのアナログ側(ADC入力のクリッピング・広帯域ノイズ)に
効く部品で、この現象はデジタル側のタイムスタンプ計算にしか出ない。C1を何Fに変えても
直らない。

## 何が可能になったか(未修正のまま記録)

修正の方向性は2通りある。**今回はどちらも実装していない。**

1. **firmware側**: `gCurrentBatch->begin()`に`timesync::nowUs()`を都度渡すのをやめ、
   前バッチの最終レコード時刻+精密な経過時間(`gFs`ベース)から次バッチの起点を
   算出する。根本修正だが`main.cpp`のバッチ管理ロジックに手を入れる
2. **API側**: `lambda/api/handler.py`の隣接点許容(`0.5〜2.0倍`)を締める(例: ±5%)。
   実装は軽いが、**締めすぎるとNTP再同期直後の正当な補正まで弾いて欠測扱いにする
   副作用がある**——「測れなかった区間を測れたように見せない」原則からは安全側だが、
   閾値の妥当性は要検討
