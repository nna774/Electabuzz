# 周波数逸脱イベント多発の原因調査と、dashboardへのハッシュルーティング追加

## きっかけ

「最近のイベントで周波数逸脱だけ異常に多い、計算誤差では」という指摘を受けて調査した。

## 計算バグではなく実際の系統変動だった

`lambda/common/grid_detect.py`のしきい値判定(`analyze()`)自体は`lambda/api/handler.py`の
`_series_payload`と同じ式(`nominal_dt`理論値を分母に使う)を複製しており、
[2026-08-09のバッチ境界ジッタ修正](2026-08-09-batch-boundary-jump-ntp-fix.md)を
そのまま引き継いでいる——ここに既知バグの再発は無かった。

実データで切り分けるため、`/events`の一番大きいイベント(peak 193mHz、2026-08-19 08:30〜)を
`series/`から生バッチ(`store_gridfreq.load_batches_in_range`)で直接引いて確認した。
`dt=1.000000s`(実測間隔が理論値と完全一致)、かつ**周波数計算とは独立な計測経路である
`v_rms_mv`(電圧)も同じ時間帯で連動して約7%沈み込み、周波数の谷とほぼ同時に底を打って
同時に回復していた**。位相計算だけがおかしくなる計算バグでは電圧側まで同時に沈む理由が無く、
これは実際に系統側で負荷急変等があった物理的signatureそのものと判断した。

**結論: `ELBZ_FREQ_DEV_THRESHOLD_HZ`(既定100mHz・3秒hold)が、実際にはこの規模で
時々起きる系統変動に対して単純に敏感すぎるだけ**——`docs/cloud.md`に元々明記されている
「しきい値はいずれも未校正の暫定値」という宿題が顕在化した形。しきい値そのものの校正は
今回のスコープ外とし、次のタスクとして残す。

## dashboardに「指定時刻表示」ハッシュルーティングを追加

上記の調査中、「イベント発生時のグラフをdashboardから見たい」という要望が出たが、
dashboardは常に「直近N分」のライブ表示専用で、過去の日時を指定するUIが無かった
(`/recent`自体は`start`パラメータに対応しているが、dashboardのJSがそれを使っていなかった)。

Namazu(nna774/NamazuHaUrokoGaNai)の`dashboard/app.js`が持つ`#live?m=&auto=&s=`という
ハッシュルーティングを、Electabuzzの単一ビュー構成に合わせて縮小移植した:

- `#start-time`(`datetime-local`)を追加。指定すると`/recent`に`start=`(指定時刻のepochマイクロ秒)
  を付けて過去の固定窓を取得する。「ライブに戻る」ボタンで解除
- `location.hash`(`#live?m=<分>&auto=<0|1>&s=<epoch秒>`)を唯一の真実にし、操作子の
  `onchange`はハッシュを書き換えるだけ、実際の再取得は`hashchange`→`route()`に集約した
  (Namazuと同じ設計)。リロード・URLの共有で表示状態が復元される
- 検知イベント一覧の行をクリックすると、そのイベントが収まる表示範囲・開始時刻へ自動で
  ジャンプする(`eventViewWindow()`)。`#minutes`はプリセット(1/5/15/30分)しか選べないため、
  継続時間+前後の余白(最低30秒、または継続時間の半分)が収まる最小のプリセットに丸める
- `#start-time`指定時は「最終受信N秒前」(鮮度表示)が実際の受信鮮度と無関係な大きな値になり
  紛らわしいため、「指定時刻表示: <日時> から」に差し替えるよう`renderStatus()`を拡張した

ローカルHTTPサーバ+Chromeで実APIに対して動作確認した。2026-08-19 15:14:19発生の
169秒イベント(→上記調査)の行をクリックし、15分窓・15:03〜15:18の範囲で実際に
49.8Hz付近まで下がる波形が描かれること、ハッシュ付きURLへの直接アクセス(リロード相当)
で表示範囲・自動更新オフ・開始時刻が復元されること、「ライブに戻る」でライブ表示に
戻ることをいずれも確認した。

設計判断の変更はない(既存の`/recent`API・`_series_payload`のロジックには一切手を
入れていない、dashboardのJSのみの変更)。
