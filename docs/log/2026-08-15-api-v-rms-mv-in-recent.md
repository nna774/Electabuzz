# `/recent`が`v_rms_mv`を返すようにした

## 何を決めたか

`lambda/api/handler.py`の`_series_payload()`が返すJSONに、`t_us`と並行な
`v_rms_mv`配列(および`latest.v_rms_mv`)を追加した。

## なぜそう決めたか

新ファームをOTAで実機投入し、`series/`に実際に`v_rms_mv`が届いていることを
S3から直接確認した(ダッシュボードにまだ出ていない、という質問がきっかけ)。
その流れで「`_series_payload()`はどのみち全レコードを`for t, r in zip(...)`で
舐めている。`r.v_rms_mv`はループの中に既にあるので、配列に足すだけなら
S3アクセスもパースも増えない」という指摘を受け、検証した。

`freq_hz`は隣接点間の差分でありsession境界・DISCONTINUITYで意図的にNoneへ
倒すが、`v_rms_mv`はレコード単体の瞬時値でその手の抑制ロジックに依存しない。
むしろ`freq_hz`より単純に済んだ——`suspect`判定を素通りしてそのまま追加すれば
足りた。

## 何が覆ったか

覆っていない。壁側(商用100V系)への換算は引き続きこのAPIの責務にしない
(→ [wire-format.md](../wire-format.md))。今回返すのはトランス二次側の
実効値[mV]そのもの、実測値であって推定値ではない。

## 次に何が可能になったか

ダッシュボードが`/recent`のレスポンスから`v_rms_mv`を直接読めるようになった。
瞬時値のテーブル表示、あるいは時間が溜まってからのグラフ化(→
[log/2026-08-15-vrms-mv-ota-live-verification.md](2026-08-15-vrms-mv-ota-live-verification.md)
の実機データで、19分間に約1%の緩やかなドリフトが実在すると確認済み)、
どちらもこのAPI変更を前提にできる。壁側換算(巻数比、現在は暫定値≈9.71倍・
未校正)の表示はダッシュボード側でopt-in(チェックボックス等)にする方針を
別途検討中——巻数比自体の再測定はユーザーが並行して進めている。
