# 2026-10-11 PPS再ロック時の外れたfsでGoertzelが13日以上動き続けていた

「電圧異常の検知が無限に出ていておかしい」という指摘から調査した。原因は電圧の
閾値ではなく、**firmwareが2026-09-27から外れた`fs`で記録窓を切り続けていたこと**で、
電圧異常・周波数逸脱の検知はどちらもその副作用だった。

## 何が起きていたか(実データ)

`/recent`と`series/`の生バッチを読んで確認した(device 1、session 29。再起動はしていない)。

| | 〜2026-09-27 09:13 JST | 2026-09-27 09:20 JST〜 |
|---|---|---|
| 周波数(5分中央値) | 49.95〜50.04 Hz | 常に50.17〜50.25 Hz |
| v_rms_mv の5分内の幅 | 約100mV | 500〜1000mV |
| 5分あたりのレコード数(`/recent`) | 300 | 298〜299 |
| バッチ末尾→次バッチ先頭の実時間 | 1.000 s | 1.127 s |
| ヘッダの`fs_measured_uhz` | 48001.70 Hz | 最終的に48001.69 Hz(正常値へ収束) |

経緯(ヘッダの`tb_obs_count`・`timebase_source`・`v_rms_mv`から):

1. 09:13:57頃からPPSエッジが約5分途絶えた(`tb_obs_count`が2206960で止まる)。
   同時刻にv_rmsが11Vから23〜25Vへ跳ねている。同日02:38〜02:53にも同様の跳ねがある。
   L ch・R ch両方への物理的な外乱と見ているが、原因は特定していない
2. 09:18:27にPPSが外れ`NTP`へ落ち、次のバッチで`PPS_NTP`に戻った。その時点の
   PPS回帰は`fs`=48373Hz・残差981µs/sで、観測数(10)と経過秒数(30)の条件だけで
   ロックを名乗っていた。外乱の偽エッジが間隔±5%の許容内に収まって回帰に入ったため
3. `main.cpp`はPPSロックの**立ち上がりの瞬間だけ**Goertzelをその`fs`で作り直す。
   回帰自体はその後正常値へ収束したが、ロックが一度も切れなかったので、Goertzelは
   約48205Hz(窓の実時間1.0042秒から逆算)を握ったまま13日以上動き続けた

窓が実時間1.0042秒なので1窓に50.21周期入り、Δcycles/公称1秒で+0.2Hzに見える。
窓が非整数周期になったことで振幅にリークが乗り、v_rmsが±5%揺れて電圧異常の
閾値(10%)を頻繁に跨いでいた。系統周波数が2週間+0.2Hzに張り付くことは物理的に
ありえないので、測定側の故障と断定した。

## 決めたこと

### firmware

- **`PpsTimebase`は確度(`residualNs`)が1ppm(`kMaxResidualNs`)以内になって初めて
  ロックを名乗る。満たさない回帰は捨ててそのエッジから取り直す。** 確度の上限を
  ロック条件に足すだけでは不十分だった。偽エッジは回帰を恒久的に偏らせ、合成
  テストでは正常なエッジを積み続けてロックした時点でも4.5ppmずれていた
- **PPSロック中、Goertzelの`fs`とPPS回帰の`fs`が2ppm(`kGoertzelRearmPpm`)以上
  離れたら作り直す。** 2ppmは周波数で0.1mHzで、測定上は無視できる。作り直しの
  たびに1窓欠けるので、ロック直後の収束で頻発しない幅にした
- **作り直した直後のレコードに`DISCONTINUITY`を立てる(ロック時の作り直しも含む)。**
  新しい推定器の最初の窓は基準点にしか使われず、1窓ぶんの位相が累積位相に
  積まれない。これを申告していなかったので、TEアンカーが欠けた位相を跨いで
  繋がりうる状態だった。判定は`pumpI2s()`で「レコードを出した推定器が前回と
  違うか」を見る形にした。Core0側でフラグを立てると、旧推定器が出した最後の
  窓がフラグを消費してしまう競合がある

### cloud(detect)

- **「直前バッチの開始→今回の開始の実時間」と「直前バッチのレコード数×公称間隔」の
  ずれを`record_cadence`イベントとして記録する(既定1000ppm超)。** バッチ内の
  レコード時刻は公称間隔で並べた値なので、窓長の異常はバッチ間でしか見えない。
  今回の故障はクラウドから4230ppmとして観測できていたのに、どこも見ていなかった
- **`record_cadence`を検知したバッチは周波数・RoCoF・電圧の判定をしない。**
  窓長が公称と違う間はどれも測定値として信用できず、判定を続けると故障が
  直るまで偽の系統イベントを出し続ける(今回の「無限に出る」そのもの)
- `docs/cloud.md`の「測定側の異常はイベントにしない」という採らなかった判断は
  維持し、記録間隔異常だけを例外にした。`DISCONTINUITY`と違い、firmwareが
  自分では気付けず、どのフラグにも現れない故障だからである
