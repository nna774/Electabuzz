# バッチ境界の針ノイズ、2回目の修正後も残っていた(3つ目の原因: 回帰更新の不連続性)

## 経緯

[powerk95との外部照合](2026-08-09-powerk95-external-verification.md)の残差を精査すると、
5点の外れ値(最大142mHz)が見つかった。時刻を並べると
`00:56:38 / 00:59:08 / 01:01:38 / 01:04:08 / 01:06:38` ——**きれいに30秒の倍数間隔**。
GFRQは1バッチ=30レコード=30秒([wire-format.md](../wire-format.md))なので、
偶然ではなくバッチ境界そのものが疑わしいと分かった。

[risks.md](../risks.md)リスク12「バッチ境界で瞬時周波数に単発スパイクが出る」は
2026-08-08に2回の修正を実機投入済みで、**2回目の修正(`framesAtEnd`化)は
「NTP問い合わせを複数回またいで境界dtが揃い続けることの確認はこれから」**という
宿題を残したままだった。今回それに答えが出た——**揃っていなかった。**

## 裏付け

`series/`から該当時間帯の生バッチをS3から取得し、ヘッダの`tb_obs_count`
(NTP観測の累積数)を時系列で並べると、5件の外れ値すべてに共通するパターンが出た。

```
00:56:08 tb_obs=9  resid_ns=2123   ← NTP観測が8→9に増えた回
00:56:38 tb_obs=9  resid_ns=2123   ← ★外れ値(49.895Hz)。dt=1.002840秒
00:58:38 tb_obs=10 resid_ns=1860   ← 9→10に増えた回
00:59:08 tb_obs=10 resid_ns=1860   ← ★外れ値(50.078Hz)。dt=0.998152秒
01:01:08 tb_obs=11 resid_ns=1536   ← 10→11に増えた回
01:01:38 tb_obs=11 resid_ns=1536   ← ★外れ値(50.074Hz)
01:03:38 tb_obs=12 resid_ns=1321   ← 11→12に増えた回
01:04:08 tb_obs=12 resid_ns=1321   ← ★外れ値(50.025Hz)
01:06:08 tb_obs=13 resid_ns=1215   ← 12→13に増えた回
01:06:38 tb_obs=13 resid_ns=1215   ← ★外れ値(50.055Hz)
```

**`tb_obs_count`が増加した(NTP観測が回帰に新しく取り込まれた)直後のバッチで、
例外なくdtジャンプが起きている。** 5/5件が一致しており偶然ではない。

## 独立な再検証で規模と性質が判明(並行セッションによる追試)

この発見をPR #18(NOMINAL区間修正)担当の並行セッションに伝えたところ、
`session_id=8`(`framesAtEnd`化を実機投入した直後、20:49:20開始のロック直後
セッション)の261境界を全数走査した独立の再検証が行われ、次の統計が出た。

| 区分 | n | 平均 | 最大 | 80mHz超 |
|---|---|---|---|---|
| tb_obs_count遷移そのバッチ | 47 | 34.0mHz | 107.6mHz | 2件(4.3%) |
| 遷移の1バッチ後 | 47 | 47.3mHz | 259.3mHz | 5件(10.6%) |
| 無関係な境界(基準) | 167 | 28.7mHz | 102.1mHz | 3件(1.8%) |

**「5/5件で例外なく」というのは言い過ぎだった。** 上記5点はたまたま全部
外れ値だった小サンプルで、実態は**遷移直後〜数十秒は異常率が上がるが
毎回ではない確率的な劣化**(80mHz超の発生率が基準の1.8%に対し遷移1バッチ後は
10.6%、約6倍)。最大値は自分が見た142mHzに対し再検証では259.3mHzが出ており、
桁は一致する——**同じ現象を見ている。**

また、この再検証は「回帰が新しい(観測数の少ない)セッション直後」を対象にしていた
点も重要。以前このリスクを「解消した」と評価した検証(2026-08-08)は**回帰が
成熟した後(観測数55〜79)のデータだけを見ていた**——後述の通り観測数が
増えるほど1点あたりの影響は減衰するため、そちらでは問題が見えなかった。
**検証対象の区間(ロック直後か、十分成熟した後か)で結論が変わる。**

## なぜ起きるか

`firmware/lib/Timebase/src/NtpTimebase.cpp`の`unixUsAt(ticks)`:

```cpp
uint64_t NtpTimebase::unixUsAt(uint64_t ticks) const {
  const double fsHz = nominalHz_ + cxy_ / cxx_;   // ← 全観測点にわたる最小二乗回帰の傾き
  const double x = (ticks - ticks0_) / fsHz;
  return unixUs0_ + x * 1e6;
}
```

`fsHz`は`addObservation()`が呼ばれるたびにWelford型で更新される回帰係数
(`cxy_`/`cxx_`)から出る。観測点が1つ増えるたびに`fsHz`自体がわずかに動くので、
**同じ`ticks`(=`rec.framesAtEnd`、物理的に同じサンプル位置)に対する
`unixUsAt()`の出力が、観測追加の前後で不連続にシフトする。**

より正確には、`unixUsAt()`は`ticks0_`(回帰の原点)からの経過時間
`x = (ticks - ticks0_) / fsHz`を外挿しているので、**`fsHz`のわずかな変化が
`ticks0_`からの外挿距離に比例して増幅される。** セッション開始直後(まだ
`ticks0_`から近い)は影響が小さいが、セッションが長時間続くほど同じ`ΔfsHz`
でも絶対時刻のズレは大きくなる方向に働く——観測数増加による1点あたりの
影響の減衰と、外挿距離の増大による増幅、**2つの効果が逆方向に効くため
単純に「時間が経てば減る」とは言い切れない。**

これは1回目の修正(粗い壁時計`timesync`の読み直しジッタ)とも、2回目の修正
(Core0の処理遅延)とも別の原因——**回帰を「今の係数で毎回引き直す」という
設計そのものに内在する不連続性**で、2回の既存修正のどちらにも対応範囲外だった。

`resid_ns`が2123→1860→1536→1321→1215と単調減少しているのは傍証になる
(観測数`tb_obs_count`が少ないうちは1点の追加が回帰係数に与える影響が大きく、
Welford更新は`n_`で割るため観測を重ねるほど1点あたりの影響は小さくなる)。
**ただし上の再検証が示す通り、これだけでは「時間が経てば消える」とは言えない**
——`ticks0_`からの外挿距離が伸びる効果と綱引きになるため、セッションが
長時間続いた場合にどちらが勝つかは未検証のまま残っている。

## 何が可能になったか(未修正のまま記録)

対策の方向性は3つ考えられる。**今回はどちらも実装していない。**

1. **firmware側(係数凍結)**: バッチ起点の計算に使う回帰係数を、バッチ生成時点で
   凍結する。前バッチ完成時の`fsHz`をそのまま次バッチの起点計算にも使い回せば、
   バッチ内・バッチ境界とも「同じ係数」になり不連続が起きない
   (ただし「凍結した係数がいつまで有効か」の設計が要る)
2. **firmware側(外挿距離の制限)**: `ticks0_`(回帰の原点)を定期的に
   ロールフォワードし、`unixUsAt()`の外挿距離を有効なNTP問い合わせ間隔
   (数分程度)以内に抑える。増幅の根を断つ方向の修正で、1より根本的
   だが影響範囲が広い(`NtpTimebase`のインターフェース自体に手が入る)
3. **API側**: `lambda/api/handler.py`の隣接点許容(現状dtが公称の0.5〜2.0倍)を
   締める、または残差を`tb_residual_ns`だけでなくバッチ単位の実測ズレとして
   正直に申告する。実装は軽いが、[2026-08-08-batch-boundary-timestamp-jump.md](2026-08-08-batch-boundary-timestamp-jump.md)
   で指摘済みの通り締めすぎるとNTP再同期直後の正当な補正まで弾く副作用がある

[open-questions.md](../open-questions.md)の該当項目は「片付いた」から未決に戻し、
[risks.md](../risks.md)リスク12も「2回目の修正でも解消せず、3つ目の原因が判明」に更新した。

**NOMINAL区間の固定アンカー化(PR #18)とは独立な問題。** PR #18はNOMINAL区間
(未規正、`timesync`直読み)の針を対象にしており、この3つ目の原因はNTPロック済み
区間(`gFs`の回帰)側の問題なので、両方の修正が別枠で必要になる見込み。
