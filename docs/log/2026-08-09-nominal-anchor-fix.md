# NOMINAL区間の針ノイズを固定アンカー方式で解消した(1970年配置バグの修正込み)

## 前回までの状態

[2026-08-08-batch-start-frame-capture-time.md](2026-08-08-batch-start-frame-capture-time.md)で
NTPロック済み区間の針は解消した(実機検証: 65分・131境界すべてdt誤差±1.3ms)。
しかし直後にPR #16(NOMINAL区間の即記録)がデプロイされ、ダッシュボードで
「NOMINAL(灰色)区間だけ針が残っている」との指摘を受けた。

## 原因の切り分け

`lambda/wire_gridfreq.py`で生バッチを直接解析し、NOMINAL区間の全レコード間隔を
計算したところ、**バッチ境界(30秒ごと)だけ一貫してdtが0.996〜1.004秒程度ズレて
いた**(バッチ内は完全に1.0000秒)。`freq = Δcycles/Δt`はdtの誤差に敏感で
(50Hzで1msのdt誤差 ≈ 50mHzの周波数誤差)、この数msのズレが〜100mHz級の
針として現れていた。

NTPロック済み区間は`gFs.unixUsAt(rec.framesAtEnd)`で直したが、NOMINAL区間は
`gFs`の回帰が使えない(未規正)ため、フォールバック先の`timesync::nowUs()`
(SNTPのSMOOTH slew補正が乗る粗い壁時計)を都度読み直す旧経路がそのまま残って
いた。これがNOMINAL側だけに残った針の正体。

## 直したこと(1回目、不完全)

NOMINAL用にも「固定アンカー+一貫した外挿」の原則を適用した。`setup()`で
i2sTask起動前(`gFrames==0`が保証される瞬間)に`timesync::nowUs()`を一度だけ読み、
以後は`gNominalAnchorUnixUs + rec.framesAtEnd / kFsNominalHz`で外挿する方式に
変更した。

## 実機投入で発覚した副作用: 1970年配置バグ

実機に焼いたところ、**S3に新しいデータが着弾しなくなった**(ように見えた)。
ingest Lambdaのログを見ると実際にはリクエストは継続して来ており、原因は
**別の場所に書き込まれていた**ことだった。`aws s3 ls`で調べると
`series/1970/01/01/00/`に大量のバッチが着弾していた。

原因: ちょうどこの時WiFiが不調で、SNTPの初回同期が`setup()`実行時点では
まだ完了していなかった(ユーザーからの報告と一致)。未同期の`timesync::nowUs()`は
UNIX epoch近辺(1970年)を返す。無条件に一度だけ読む方式だと、**この悪い値が
NOMINALセッション全体に固定されてしまう**——旧来の「都度読み直す」方式なら
次に読んだときに正しい値へ自己修復していたが、固定アンカー化したことで
この自己修復能力を失っていた。

## 直したこと(2回目、これが最終形)

アンカー取得を**`timesync::isSynced()`が初めてtrueになった瞬間まで遅延**させる
方式に変更した。`gNominalAnchorUnixUs`の初期値を0(未取得)とし、バッチ開始の
たびに「まだ未取得かつ同期済みなら今取得する」をチェックする。同期前に生成される
バッチは(旧来同様)`timesync::nowUs()`への素朴なフォールバックのままだが、
**悪い影響は「同期が完了するまでの数バッチ」に限定され、以後は良いアンカーで
一貫する**——固定アンカー化前の「都度読み直し」と同程度の劣化に留め、
かつ一度同期が完了すれば以後は完全に安定する、という両立を実現した。

## 何を確認したか

実機に焼き直し(00:34:33)、S3を確認:
- **1970年配置は00:33:55を最後に止まり、00:35:37から正常な日付
  (`series/2026/08/08/15/`)に着弾している**
- 新セッションの境界dtを`lambda/wire_gridfreq.py`で解析: **5境界すべてdt=1.0000
  (stdev=0)**。固定アンカーからの純粋な線形外挿なので原理的にジッタが入らない
- 全区間(境界含む)での最大周波数偏差は59mHzで、実信号の正常なばらつき範囲内
- ダッシュボードの目視でも、NOMINAL区間(灰色線)の棘が消えたことをユーザーが確認

## 何が可能になったか

[risks.md](../risks.md)のリスク12を解消済みに更新した。NTPロック済み・NOMINALの
両区間で、バッチ境界の針ノイズという当初の問題(→
[2026-08-08-batch-boundary-timestamp-jump.md](2026-08-08-batch-boundary-timestamp-jump.md))
が完全に解消したと言える状態になった。
