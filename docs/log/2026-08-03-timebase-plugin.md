# 2026-08-03: GNSS を待たずに走らせる — 時間基準をプラグインにする

## 問い

「GNSS の PPS はそのうち注文するとして、一旦なしでクロックのまま動かせないか。
部品が届いたらそれを繋ぐようにするとして」

## 決めたこと

**動かせる。条件は一つだけで、`fs` を定数として書かないことだ。**
時間基準を3実装のプラグインにする。

```
TimebaseEstimator (interface)
  fsMicroHz()     現在の実効サンプルレート推定 [µHz]
  residualNs()    推定の 1σ [ns/s] — 確度の自己申告
  obsCount()      推定に使った観測数
  source()        NOMINAL / NTP / PPS
```

| 実装 | いつ使う | 確度 | 偽TE |
|---|---|---|---|
| `NominalTimebase` | フェーズ1の疎通確認だけ | ±20〜100ppm | 1.7〜8.6 秒/日 |
| **`NtpTimebase`** | **GNSS 到着まで。かつ到着後も残す** | 0.1〜1ppm（1日窓） | **10〜90 ミリ秒/日** |
| `PpsTimebase` | GNSS 到着後 | ppb級 | µs/日 |

## なぜ NTP で「暫定」以上のものになるのか

系統時刻偏差の実変動は秒オーダーなので、**偽TE が数十ms なら信号より1〜2桁小さい。
つまり NTP 時間基準の TE は意味のあるデータになる。**

設計書は元より「NTP は原理的には足りる（1日窓で 0.06ppm）」と認めていて、
退けた理由は確度ではなく**検証可能性**だった。**暫定運転の時間基準としては、
その留保は問題にならない。**

**往復遅延の非対称バイアスは、定数なら回帰の傾きに乗らない**（切片に乗るだけ）。
効くのはバイアスの時間変動だけで、これは経路変動オーダー。ここが 1ppm を切れる根拠。

## なぜ捨て仕事にならないのか — 到着後も3つの役割が残る

1. **PPS 喪失時の holdover。** リスク5（屋内で fix を維持できるか）に対して、
   設計書はこれまで「フラグを立てて捨てる」しか答えを持っていなかった。
   **NTP 時間基準があれば fix が落ちた区間を 1ppm 級で埋められる。空白ではなく劣化として扱える**
2. **`fs` の独立クロスチェック。** PPS と NTP は物理的に無関係な経路で同じ `fs` を推定する。
   一致すれば方式Aが効いている証拠、食い違えばどちらかが壊れている。
   **二重測定を諦めた本設計に、時間基準についてだけ二重系が手に入る**
3. **自分がどの水晶に乗っているかの実測**（下記の新発見）

## 実装上の落とし穴: システム時刻に回帰してはいけない

`SNTP_SYNC_MODE_SMOOTH` は**システム時刻の進む速さ自体を制御対象にしている。**
それに回帰したら、測っているのは水晶ではなく slew ループだ。

**測定専用の SNTP クライアントを別に持つ。** システム時刻を一切触らず、
`(累積サンプル数, NTP時刻, RTT)` の三つ組を記録して自分で回帰する。
RTT の大きい標本を捨てられるのが自前実装の利点。
バッチのタイムスタンプ用のシステム時刻は従来どおり SMOOTH のままでよい。**役割を分ける。**

## wire format を今のうちに源非依存にした

**まだ1バイトも記録していないうちがやり時だった。**

| Offset | 変更前 | 変更後 |
|---|---|---|
| 44 | `pps_count` | `tb_obs_count` — PPS エッジ数 **または** 採用した NTP 標本数 |
| 48 | `pps_residual_ns` | `tb_residual_ns` — 時間基準推定の 1σ [ns/s] |
| 54 | reserved | **`timebase_source` (u8)**: 0=NOMINAL / 1=NTP / 2=PPS / 3=PPS+NTP |
| 55 | reserved | `soc_temp_c` (i8) — 事後の `fs(T)` 補正の材料 |

**すべて予約領域から出したので、GNSS が来た時点でヘッダは1バイトも変わらない。**
後段のパーサもダッシュボードも書き直さない。

**`timebase_source` は絶対に省けない。** これが無いと「このデータは規正済みか」が
永久に判別できなくなり、「測れなかった区間を測れたように見せない」という一線が破れる。

## TE は「保存する、提示は封じる」

累積位相は**どの時間基準でも有効な物理量**だ（サイクルを数えただけ）。保存は無条件に行う。
封じるのは派生量である TE の**提示**の方。

| `timebase_source` | ダッシュボード |
|---|---|
| `NOMINAL` | TE を描かない。周波数変動の形と RoCoF だけ |
| `NTP` | 描く。ただし ±(`tb_residual_ns` × 経過時間) の不確かさ帯を必ず併記（1日で ±10〜90ms） |
| `PPS` | 帯が µs 級に潰れる |

**グラフの上で帯が縮む瞬間が、GNSS を繋いだ日になる。それが一番正直な見せ方だ。**

## 新発見（覆ったこと）: そもそも `fs` を決めているのは誰か

**設計書はこの問いに答えを持っていなかった。**
PCM1808 は動作モードに関わらず SCKI（システムクロック、256/384/512 fs）を要求する。

- **モジュールに 12.288MHz の缶発振器が載っている個体は、それが master になる。**
  fs は 48kHz ちょうどだが、確度は**その缶発振器の公差（安価品で ±50〜100ppm、温度特性も悪い）**
- **ESP32 から MCLK を出す構成なら、fs は分数分周器で決まる。** 48kHz は 160MHz 系から
  割り切れないので、**公称 48000 と実際の設定値が数十ppm 食い違う。水晶とは無関係な誤差だ**

**「48000 と書いてある値」は二重に信用できない。** リスク10 として追加した。

**方式Aはどちらの水晶が master でも成立する。** 相殺は「信号と時間基準が同一クロックで
測られている」ことだけに依存し、そのクロックの出自を問わない。
**だから master/slave の選択は方式Aの成否に効かない。効くのは PPS が無い期間の確度だけだ。**

## 後戻りできないのは R ch だけ

- **I2S は最初からステレオで初期化する。** GNSS 未入手で R ch が未接続でも同じ。
  モノラルで作ると DMA のバッファレイアウト・サンプルの添字・後段の処理が全部変わり、
  **PPS を繋ぐ日に一番バグを埋めやすい変更になる**
- R ch の分圧・帯域制限・PPS 用ピンヘッダを基板に最初から載せる（部品5点）
- **未接続の R ch を浮かせない。** バイアス網で Vcc/2 に落とす。
  浮かせるとハムを拾い、「PPS らしき波形」が見えて無駄に悩む
- 捨てるのではなく R ch のノイズフロアを記録しておく。PPS を繋いだ日の S/N の比較対象になる

## 併せて決まったこと

- **共有レポ名は `batch-uplink`。** Python パッケージは `batch_uplink`。
  設計書で唯一残っていた未決事項（`<shared>` プレースホルダ）が閉じた
- **手持ちハードウェアは ESP32-S3 のみ。** PCM1808 も未入手で要発注

## 次に何が可能になったか

**PCM1808 を待たずに `NtpTimebase` を書ける。**
時間基準の回帰は「**単調増加するティック源**を NTP 時刻に回帰する」処理であり、
**そのティックが I2S のサンプル数か `esp_timer` の µs かを問わない。**

- ティック源をインターフェイスにしておけば、`esp_timer` → I2S サンプル数 → PPS の
  差し替えが全部同じ形になる
- **数日走らせるだけで手元の ESP32-S3 の水晶の実 ppm と温度相関が取れる。**
  これはリスク10 の片方の候補の実測値そのもので、
  PCM1808 が届いた日に缶発振器と比較する基準が先に手に入る
- 測定専用 SNTP クライアント・RTT フィルタ・回帰・残差の 1σ 算出は
  全部この段階で書き切れてテストも書ける

**着手可能タスクが2本になった。** `batch-uplink` の切り出し（優先度上）と、
`NtpTimebase`（切り出しの検証待ち時間に走らせる）。
