# NOMINAL区間（起動直後〜NTPロックまで）の扱いを開いた問いとして記録

## 経緯

実機は`env:record`起動後、`NtpTimebase`が`kMinObs=8`・`kMinSpanSeconds=600`
（[NtpTimebase.h](../../firmware/lib/Timebase/src/NtpTimebase.h)）を満たし
`gFs.source() == kNtp`になるまでGoertzelを起動しない
（[main.cpp](../../firmware/src/main.cpp)、コメント「fsがNTPで規正できるまではGoertzelを
起動しない。測れていない精度で『測れた』ように見せない」）。この間、記録・送信は完全に
停止し、起動直後の約10分間のデータが欠落する。

これは意図した設計（[timebase.md](../timebase.md)の不変条件）だが、なぜ「NOMINALタグを
付けて記録し、表示側で封じる」という、ワイヤフォーマットが既に用意している道
（`timebase_source`、`NOMINAL`時は「TEを描くな、周波数変動の形とRoCoFだけ出す」
→ [timebase.md 209-216行](../timebase.md)）を使わないのか、という問いが上がった。

## 分かったこと

- **TEと違い、GFRQ本体の周波数値自体はNOMINAL区間では表示封じだけで救えない。**
  `fs`誤差は測定周波数の誤差にそのまま1:1で乗る（`timebase.md 12-27行`の定量根拠）。
  規正前は実測で数十ppm級ずれており（`gXtal`/`gFs`実測、`docs/risks.md`）、
  50Hzに対して1〜数mHzの**系統的な**誤差になる。目標±1mHzを超えており、
  ノイズと違って平均しても消えない。TE（保存はする・提示は封じるだけで済む派生量）と
  GFRQ本体（値そのものが常に出力される一次データ）とでは、`timebase_source`タグの
  効き方が違う。
- **「起動直後からNOMINALで即記録→600秒後にNTPへ切替」という案を比較検討した記録は
  リポジトリ内に見当たらなかった。** 現行の「NTPロックまで一切記録しない」という
  より厳しい実装を採った理由は、上記の定量的根拠から間接的に読み取れるのみ。
- **代案として、事後補正の可能性がある。** NTP回帰が600秒後にロックした時点で、
  その回帰は**その600秒間全体にフィットした傾き**を持っている。これは`timebase.md`の
  「事後補正の余地を無料で残す」節（SoC温度を記録してGNSS到着後に`fs(T)`特性を遡って
  適用する話）と同じ発想をNTPロック前後の境界にも広げるもの。ただし
  **「生サンプルを保持する」は容量的に成立しない**——48kHzステレオ・4B/frame換算で
  約192KB/秒、600秒ぶんで約115MB。N16R8のPSRAMは8MBしかなく、40秒ぶんしか貯まらない。
  実際に検討に値するのは下記の2案。

## 候補案（比較検討用、いずれも未実装）

**案A: NOMINALで即記録・即送信 + NTPロック後に補正レコードを別送**
- firmwareは起動直後からGoertzelを動かし、その時点のベスト推定`fs`（`source=NOMINAL`）で
  バッチを通常のケイデンス(30秒間隔)のまま送る。正直に`timebase_source=NOMINAL`と申告する
- 600秒後にNTPがロックしたら、「このセッションのこのカウント区間は確定`fs`に対して
  εppmずれていた」という小さな補正レコードを追加で1本送る
- 補正の**適用**は`lambda/store_gridfreq.py`・ダッシュボード側の仕事になる。元のNOMINAL
  レコードと補正レコードを読み出し時に突き合わせて直す
- 利点: firmware側のメモリコストがほぼゼロ。データがリアルタイムに(粗い精度で)見える
- 欠点: ダウンストリーム（ワイヤフォーマット・ストア・ダッシュボードの3箇所）に
  「後から直す」ロジックを新規に持たせる必要がある

**案B: window単位のGoertzel出力だけを一時保持し、ロック後に補正してから送る**
- 生サンプルではなく、**Goertzelが吐いた後のwindow(1秒)ごとの位相/周波数値**
  （データ量は生サンプルの何桁も小さい）を一時保持する
- 600秒後に`fs`が確定したら、保持していたwindow結果へスカラー補正をかけてから、
  `timebase_source=NTP`として初めて送信する
- 利点: 送信されるデータは常に「補正済み」。ダウンストリームは無改造で済む
- 欠点: 起動直後の約10分間は依然としてデータが即時には見えない
  （送信が遅れるだけで欠落はしない）

**両案共通の前提を検証した。** どちらも「`fs`が間違っていたときのGoertzel出力は、
後からスカラー1個掛ければ真値に戻る」という仮定に乗っている。[tools/check_fs_linearity.py](../../tools/check_fs_linearity.py)
で、真の系統周波数50.000Hzを物理サンプルレート`fs_true = 48000×(1+ε)`で生成し、
firmwareが未規正時にやるのと同じく`fs=48000`(nominal、わざと間違った値)を渡して
`goertzel_cycles()`(`tools/gridfreq/goertzel.py`、本番の参照実装そのもの)に食わせ、
出力`freq_hz`の系統誤差(bias)を`ε`(-1000〜+1000ppm)に対して線形回帰した。
**結果: R²=0.99999939、±1000ppm(現実の水晶誤差の10倍以上)まで振っても
線形予測からの残差は最大0.040mHzで、目標精度±1mHzの1/20以下。** Goertzelの再帰フィルタ
のビンミスチューニングによる非線形性は実用上問題にならないと確認できた。**案A・Bの前提は
成立する。** 検証スクリプトは`tools/check_fs_linearity.py`としてリポジトリに残してあるので、
`.venv/bin/python tools/check_fs_linearity.py`で誰でも再現できる。

## 決定

**案Aを選ぶ。** NOMINALで即記録・即送信し、NTPロック後に補正レコード(εppm、対象の
カウント区間)を別送する。ダッシュボードは以下の表示にする:

- NOMINAL区間はそれと分かる線の引き方(色/線種を変える)で描く
- 補正レコード到着後、その区間に「補正した予測値」の線を重ねて描く(未確定だった値を
  遡って埋める形。ただし生の値そのものではなく補正済みの派生値だとわかる描き方にする)
- NTPロック後(切替後)は今まで通りの線に戻る

理由: 案Bより即時性が高く、firmware側のメモリコストもほぼゼロ。線形性が確認できた今、
案Bの利点(ダウンストリーム無改造)より、案Aの利点(データがリアルタイムに見える)を
優先する。ダウンストリーム側の実装コスト(補正の適用ロジック)は許容範囲と判断した。
