# AFE実配線とfs実測 — リスク10の解消

## やったこと

`docs/hardware.md` の確定部分（AFE分圧R1/R2 → PCM1808 L IN、AC OUTリターン→GND直結、
電源5V/3.3V、I2Sデジタル4本 SCK/BCK/LRC/DOUT）を実配線した。TVS・C1（2次LPF）・Vcc/2
バイアス網はOPアンプ未選定のまま据え置き、FMT/MD1/MD0も配線図の通り開放のままにした。

配線に着手する前に、走行中だった `soak/soak-20260804.csv` の捕捉プロセスを確認したところ、
既にポートを見失って失敗ログを吐き続けているだけの状態だった（`kill` で正式停止）。一昼夜
ぶんの結果（[2026-08-05のログ](2026-08-05-soak-first-day.md)）は既に確保済みなので損失はない。

`firmware/src/main.cpp` v2（`gXtal`=水晶ppm、`gFs`=fs実測ppmを同じNTP標本から同時推定）を
実機に焼き、シリアル出力をNTPクエリのたび（約128〜192秒間隔）に監視した。

## 分かったこと

### 1. 配線は生きている

`ovf`は全区間で0（DMA溢れ・フレーム損失なし）。トランス接続前は `l_pp`/`r_pp` がほぼ0
（DOUTは生きているが無信号）、トランス接続後は非ゼロに変化した。DOUTの死活と実配線の
両方をこれで確認できた。

### 2. 序盤の異常値はC1未実装によるノイズ、破壊リスクではない

トランス接続直後の数分間、`l_pp`/`r_pp` がフルスケール(16,777,215コード)に張り付いた。
一方でDMMでPCM1808 L INを直接測ると約0.6VAC——設計計算(分圧比k≈0.0576、無負荷実測
29.1Vppから逆算)と整合する正常値だった。DMM(低帯域の実効値計)では見えず生ADCでは
見える、という食い違いから、**C1(LPF)が未実装のハイインピーダンスな分圧ノードが広帯域
ノイズを拾っていた**と判断した。`hardware.md`に「R1を100kΩ側に寄せたのは万一の異常時の
電流制限を優先したため」と明記済みで、この抵抗値のおかげでクランプ電流は最悪でも
数百µAに収まり、破壊リスクにはならないと判断した。C1の実装自体は引き続き未着手
（OPアンプ選定待ち）。

### 3. リスク10を解消: SCKIはESP32のMCLK駆動と判定

`NtpTimebase`の収束条件(`kMinObs=8`, `kMinSpanSeconds=600`)を満たした`n=8`以降、
`source`が`NOMINAL`→`NTP`に切り替わり、同時に`l_pp`もフルスケール張り付きから抜けて
妥当な値（フルスケールの約48%、L INで約1.4Vpp相当）に落ち着いた。以後n=17まで安定継続。

`gXtal`と`gFs`のppmは**一致しない**——だが差分（`gFs - gXtal`）は8点にわたって
31.7〜32.9ppmとほぼ一定だった（`gXtal`自体は2.66〜4.39ppmの間で毎回動いていたにも
関わらず）。これは`docs/timebase.md`が事前に指摘していた「48kHzは160MHz系PLLの分数
分周器で作られ、公称値との間に**水晶とは無関係な**数十ppmのずれが生じる」という予告と
定量的に一致する。差分が一定であること自体が、`gFs`と`gXtal`が同じ水晶に紐づいている
（＝ESP32のMCLKがSCKIを駆動している）ことの証拠になる。モジュール搭載の缶発振器が
masterなら、この差分は無関係な2つの水晶のppmの差になり一定になる理由がない。

`gXtal`は収束するにつれ2026-08-05のsoak実測値(+3.8873ppm)に接近した（n=17時点で
+3.9959ppm、差0.11ppm）。短時間のNTP回帰でも既知の基準値と整合したこと自体、今回の
計測が信頼できることの裏取りになる。

### 4. 電圧チェーンの整合を確認

100V商用(2√2×100V≈282.8Vpp) → トランス(実測10.3VAC無負荷、定格9VAC) → 分圧
(R1/R2+ADC負荷) → ADC生コード、の各段が桁・係数とも矛盾なく繋がることをユーザーと
検算した。無負荷実測(29.1Vpp)と定格計算(25.4Vpp)の間に、負荷あり(分圧回路経由)の
逆算値(約24.3Vpp)が収まったのも、小型トランスの無負荷ブースト挙動として自然。

### 5. NtpTimebaseの外れ値排除が実機で機能した

1回、NTPクエリのRTTが異常値(86929、通常は25000〜35000)になった際、`n`/`fs_ppm`が
更新されず`rejected`が1増えた。判定はコメント通り`NtpTimebase`内部のRTT/外れ値排除に
委ねられており、想定通り動作した。

## 覆ったこと

`progress.md`の「着手可能なタスク」に書いていた判定基準
「`fs_ppm`が`ppm`(水晶側)と**一致すること**」は不正確だった。実際には一致せず、
**差分が一定であること**が正しい判定基準だった。`docs/timebase.md`の「見落としていた
前提」節はこの可能性を既に指摘していたが、`progress.md`側の要約がそれを反映していな
かった。`progress.md`の該当箇所を訂正する。

「一致・不一致を語るのは半日待ってから(`fs_resid_ns`が0.1ppm級に落ちるまで)」という
当初の計画も、結果的には約42分・17サンプルの定性判定（差分の一定性）で十分だった。
ただし`fs_ppm`の**値そのもの**を水晶と同等の精度(±0.005ppm級)で欲しい場合は、
`gXtal`のときと同様に長時間soakが別途必要——今回はそこまではやっていない。

## 次に何が可能になったか

リスク10が解消されたことで、`fs`の長期安定度は水晶soakの実績(0.2ppm級)がそのまま
使える見込みが立った。配線（AFE確定部分・電源・I2S）が実機で生きていることも確認済み。

残っている宿題:
- C1(LPF)・TVS・Vcc/2バイアス網の実装（OPアンプ選定待ち、引き続き未着手）
- モジュール入力のDC電位実測（open-questions.mdに残っている問い。Vcc/2バイアス網の
  要否判定に使う。今回はAC電位のみ確認した）
- `fs_ppm`の高精度化が必要なら、水晶と同様の長時間soakを別途行う
