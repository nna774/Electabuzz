# 2026-08-12 AC入力線のブレッドボード脱落と検知方針

## 何があったか

実機のAC入力線（トランス二次側→AFE R1への配線）がブレッドボードの差し込みから
物理的に抜けた。検知できるか、そもそも抜けないようにできないかという問いが出た。

## 断線時にAFEがどう振る舞うか

現行AFE（[hardware.md](../hardware.md)「アナログフロントエンド」節、C1実装後・
Vcc/2バイアス網なし確定後の構成）で考える。

```
AC出力 ── R1(100k) ──┬── R2(6.8k) ──┬── GND
                      │(node A)      │
                    [TVS未確定]     C1(15nF)
                      │              │
                      └─ PCM1808 L IN ┘
```

入力線が抜けるとR1の上流が浮くが、**node Aは引き続きR2(6.8kΩ)経由でGNDに
低インピーダンスで繋がっている。** つまり「静かに0Vへ落ちる」だけで、
2026-08-07に観測した「C1未実装時にnode Aが高インピーダンスで広帯域ノイズを拾い
フルスケールに張り付く」現象（→
[log/2026-08-07-fs-wiring-verification.md](2026-08-07-fs-wiring-verification.md)）
とは別物——あちらはC1が無かった期間限定の過渡現象で、今の回路には当てはまらない。

**結論: 入力断は「暴れる」のではなく「振幅がゼロに落ちて静止する」という
素直な壊れ方をする。** これはソフトウェアで検知しやすい部類の故障モードだ。

## 検知方針（未実装、方針のみ）

Goertzelは単一ビンのエネルギーを既に計算している。振幅がしきい値未満の状態が
一定時間（数周期〜数秒オーダー）続けば「入力断」と判定できる見込み。

これは「測れなかった区間を測れたように見せるな」という設計全体の不変条件
（[CLAUDE.md](../../CLAUDE.md)3章）の一適用例として扱うのが筋がいい——
timebase_sourceが「時間基準の質」を申告するのと同じ立て付けで、
「入力そのものが生きているか」も申告すべき品質の一種。

実装先の候補は`GFRQ`の`flags`（現状ビット未割当、→
[open-questions.md](../open-questions.md)「設計を進めると決まること」）。
位相推定側の実装が固まった今、この用途で1ビット割り当てるのは妥当な選択肢になった。

## 物理対策（未実装、方針のみ）

検知を実装しても「測れない区間が増える」だけで根本対策にはならない。
ブレッドボードは常時稼働機の入力段としてそもそも脆弱——恒久対策は
半田固定・端子台・ホットボンドでの線の固定など、ブレッドボードへの
依存自体を下げる方向で検討する。

## 通知(検知したら知らせる)を足したい、という追加の要望

検知だけでなく「抜けとるやんけ！」と通知まで送りたいという話が出た。ここで
「これって停電した際にも抜けていると判定されるよね？」という指摘が出て、
検討し直した。

**AFE単体の信号では、入力線の断線と停電は原理的に区別できない。** どちらも
node Aが振幅ゼロで静止するという同じ見え方になる（上の断線時の解析がそのまま
当てはまる）。今は停電すればESP32自体もそのAC電源系統から給電されているため
装置ごと止まり、通知を送る主体がいなくなるので実害はない。だが**UPS化
（→ [log/2026-08-11-usb-ups-power-mux-design.md](2026-08-11-usb-ups-power-mux-design.md)）
後はESP32が電池で生き続け、AFEだけが入力ゼロを見る状態になる**——このとき
断線と停電は見分けがつかなくなる。

**方針: 無理に区別しない。** 追加の手掛かり(例えば別系統でコンセントの
生死を見る)を足さない限り自動判別はできない。「AC入力が見えない」という
ひとつの通知にして、原因の切り分けは通知を受けた人間が現地を見て判断すれば足りる。
停電そのものも系統の話としては無関係ではないので、無理に作り分けて複雑にする
理由が今のところ無い——具体的な区別の要求が出たときに初めて考える。
