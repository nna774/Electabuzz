# 2026-08-13 電源喪失検知まわりのドキュメント整合

## 何があったか

LEDやピエゾでの通知を検討する相談から、「電源喪失検知のログはどこか」を辿ったところ、
ローカルの`main`がorigin/mainより18コミット遅れており、[2026-08-12のAC入力線断線検知ログ]
(2026-08-12-afe-input-disconnect-detection.md)を含む一連のマージを持っていなかったと判明。
`git pull --ff-only`で追従した後、`docs/hardware.md`の「電源」節が同ログの結論に
更新されていない食い違いを見つけた。

## 直したこと

1. **`docs/hardware.md`「電源」節**: 「停電検出時(v_rms低下)は明示記録」という
   古い記述を、2026-08-12の結論(Goertzelビンエネルギーのしきい値割れで検知、
   ただし断線と停電はAFE単体では区別できないため「AC入力が見えない」で一本化、
   人間が原因を切り分ける)に合わせて書き換えた。`kGfrqFlagPowerFail`
   (`GfrqHeader.flags`のビット3、バッチ単位の粗い指標)が既に予約済みだが
   未配線であることも明記した
2. **STATピン(UPS電源マルチプレクサ案)の位置づけを修正**: 「STAT+AFEの組み合わせで
   断線/停電を自動判別できるのでは」という案が本セッションの相談中に出たが、
   ユーザー指摘で誤りと判明した——STATは母艦(ESP32)自身の給電経路、AC入力断検知は
   トランス→AFEの経路で、**物理的に別系統ゆえ連動しない**。反例: USB配線を
   整理する際にUSBだけ一時的に抜くと、トランスは生きたままでもSTATは電池側に
   切り替わる。**方針: STATを記録するとしても`timebase_source`と同じ独立した
   品質ビット止まりとし、自動判別の根拠にはしない。** `hardware.md`・
   `open-questions.md`の両方に反映した
3. **`v_rms_mv`が空である理由を明確化**: 「意味が未定義だから測れないのでは」
   という問いに対し、**測る能力自体は既にある**と確認した。
   `GoertzelEstimator::magnitude()`(`firmware/lib/Goertzel/src/Goertzel.h:55`)が
   窓ごとのビン振幅を計算済み(現状は起動時の50/60Hz判別にしか使っていない、
   `firmware/src/main.cpp:533`)。AFEの分圧比もR1=100kΩ/R2=6.8kΩで確定済み。
   ブロッカーは新規計測ではなく、**基準点(u16 mVに100V商用は収まらないので
   トランス二次側基準にするか等)の決定と、ADCコード→volt換算の配線**だけ
   (→ [open-questions.md](../open-questions.md)「`v_rms_mv`の基準点」)

## 教訓

**ローカルブランチが古いと「議論が無かった」ように見える。** 検索の失敗と
区別がつかないので、横断的なドキュメント検索の前に`git fetch`+`git log HEAD..origin/main`
で遅れを疑うのが安全。今回は18コミット遅れており、直近3日分のログ・
terraformの変更を丸ごと見落としていた。
