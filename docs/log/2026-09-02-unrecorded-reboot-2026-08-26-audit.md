# 「実機ではまだpanic/WDT再起動事例が無い」を検証したら、記録漏れの再起動が1件見つかった

## 背景

なまずのコアダンプ機構調査(→ [2026-09-02-namazu-coredump-review.md](2026-09-02-namazu-coredump-review.md))
の結論で「Electabuzzの実機ではまだpanic/WDT再起動によるクラッシュ事例が報告されて
いない」と書いたところ、ユーザーから「それは実際に測ったのか、気付いていない
可能性はないか、再起動したら通知が来るから分かるのか」と指摘された。**確認せずに
`docs/progress.md`に事例が無いことだけを根拠に書いていた**ため、実データで検証した。

## 検証方法

1. `electabuzz-devices`(DynamoDB)を直接scanし、`boot_epoch_us`と
   `boot_epoch_notified_us`が一致していること(=直近の再起動はwatchdogが処理済みで
   未通知の差分が残っていないこと)を確認した。
2. これだけでは過去の履歴が分からないため、`tools/check_pps_soak.py`
   (`series/`の実バッチを直接読み`session_id`変化を機械的に検出するツール)を
   watchdog Lambda運用開始(2026-08-16)から現在まで走らせ、**全期間の再起動を
   洗い出した**。

## 見つかったバグ: `check_pps_soak.py`は8日を超える範囲を警告なく打ち切る

`--start 2026-08-16 --end 2026-09-02`(約17日)を指定したところ、`対象バッチ数`は
23040件(=ちょうど192時間=8日ぶん)で止まり、**エラーも警告も出さずに** 8/16〜8/23
だけを見て「イベントなし」と返した。原因は`lambda/s3keys.py`の
`series_hour_prefixes()`が`MAX_HOUR_PREFIXES = 24 * 8`(8日)でプレフィックス列挙を
打ち切っているため——これは元々`/recent`のようなAPI呼び出しが暴走して大きすぎる
範囲を投げてくることへの多重防御(コメントに明記)だが、**オフライン解析ツールの
`check_pps_soak.py`もこの定数を無条件に共有しており**、長期監査で静かに不完全な
結果を返す。8日以内のチャンクに分けて手動で回避し、8/16〜8/23・8/24〜8/31・
8/31〜9/2の3回に分けて全期間を洗い直した。**この打ち切りバグ自体は今回は
直していない**——`check_pps_soak.py`側で範囲が`MAX_HOUR_PREFIXES`を超えたら
エラーで落とすか、内部で自動的にチャンク分割するかの対応が要る。

## 見つかった再起動: 2026-08-26 20:14〜20:23 UTC(記録漏れ)

3チャンクの結果:

- 2026-08-16〜08-23: イベントなし
- **2026-08-24〜08-31: 2026-08-26 20:14:28 UTC に欠測ギャップ466秒、
  20:22:43 UTCに`session_id: 27 -> 28`(再起動)、直後`timebase_source`が
  `PPS_NTP -> PPS -> PPS_NTP`(30分弱でNTP再規正)**
- 2026-08-31〜09-02: 2026-09-01 10:58:36 UTCに`session_id: 28 -> 29`
  (**既知**——measurementTask分割PR #91のOTA配信による計画済み再起動、
  → [2026-09-01-measurement-task-split-ota-deploy.md](2026-09-01-measurement-task-split-ota-deploy.md)
  に記録済み)

**2026-08-26の再起動は、`docs/progress.md`にも`docs/log/`にも一切記録が無かった。**

## 2026-08-26の再起動の性質: 電源断ではなくファームウェア側の再起動と判断

前後のバッチを直接取得して照合した:

| | 直前(20:14:28 UTC) | 直後(20:22:43 UTC) |
|---|---|---|
| `session_id` | 27 | 28 |
| `timebase_source` | PPS_NTP | PPS |
| `v_rms_mv`(末尾レコード) | 10216 | 10249 |
| `power_fail`フラグ | 立っていない | 立っていない |

`v_rms_mv`は直前直後とも約10.2〜10.25V(正常値)で連続しており、AC入力断検知
(`kGfrqFlagPowerFail`)も発火していない——**電源(AC入力)は途切れていないと判断できる**。
CloudWatch Logs(`electabuzz-ingest`)の`uptime_us`テレメトリでも、直前が
`968180046135us`(≈269.5時間)、直後が`424838090us`(≈7.1分)で、**ESP32自体の
稼働時間カウンタがゼロ近くにリセットされている**——AC電源は生きたまま、
**ファームウェア自身が再起動した(WDTパニック等の可能性が高い)**と見るのが
自然。ただしElectabuzzのfirmwareは`reset_reason`(なまずの`X-Namz-Reset-Reason`
相当)を送っておらず、**panicかWDTか意図しない`ESP.restart()`かは区別できない**。

watchdog Lambda(`electabuzz-watchdog`)のCloudWatch Logsを見ると、20:23:16 UTCの
呼び出しだけ754msと他の呼び出し(110〜160ms程度)より明らかに長く、外部への
Slack POSTが乗ったと推測される時間差になっている(2026-09-01の既知OTA再起動でも
同じ「該当呼び出しだけ長い」パターンを確認済み)——**watchdogは実際にこの再起動を
検知しSlack通知を送った可能性が高い**。ただし実際にSlackへ届いたかは
CloudWatch Logsだけでは断定できない(ログに通知内容を出力していないため)。

## 結論・訂正

- **「実機ではまだクラッシュ事例が無い」は誤りだった。** 少なくとも1件、
  2026-08-26に電源断を伴わない未記録の再起動があった。
- **監視の仕組み(watchdogの再起動検知)自体は機能していたと見られる**——検知漏れ
  ではなく、**Slack通知が来ても`docs/`に記録する運用が徹底されていなかった**
  ことが本質的な問題。
- コアダンプ機構の優先度は、この事実を踏まえて見直す価値がある
  (→ [open-questions.md](../open-questions.md)「コアダンプ自動収集・アップロード」
  の項を更新)。**ただしコアダンプ機構が無くても、なまずが送っている
  `reset_reason`ヘッダ(`X-Namz-Reset-Reason`相当)だけなら遥かに低コストで
  追加でき、次にこの種の再起動が起きた時にWDT/panic/意図しないrestartの
  切り分けだけは即座にできるようになる**——コアダンプ本体より先に着手する
  価値がある候補として残す。
- `check_pps_soak.py`の8日打ち切りバグは、今後同種の長期監査をする時に
  再び踏む。直すか、せめて警告を出すかの対応が要る。
